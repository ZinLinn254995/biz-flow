# P4.1 — Sync-Ready Domain Contracts

## Status

P4.1 is a provider-neutral contract foundation. It does not implement authentication, networking, cloud storage, synchronization queues, migration execution, conflict UI, encryption, or multi-device behavior.

## Approved owner decisions

- Anonymous local use remains permanent and does not require an account.
- Future local-to-account association is explicit, reviewed, and never silent.
- Signed-out retained data is conceptually locked/encrypted; implementation is deferred.
- Conflicts use record-level optimistic versioning with explicit surfacing; no unrestricted last-write-wins or automatic field merge.
- Synchronization rolls out entity-by-entity.
- Destructive account operations require export/recovery before deletion.
- Provider evaluation and selection occur after P4.1.

## Entity classification

All current domain entities are classified as `SYNCHRONIZED` because they are durable business or personal finance records that must eventually be available across authorized devices. `SaleItem` is an embedded sale aggregate component, not an independent repository entity. There are currently no domain entities classified `LOCAL_ONLY` or `DEFERRED`; device/session/queue metadata is future infrastructure, not an invented domain entity.

The executable classification is `src/types/syncContracts.ts`.

## Ownership and identity

Current local records retain their client-generated stable UUIDs. Anonymous records are owned by the local installation conceptually; account ownership is represented only as a future contract and requires an explicit reviewed migration. An account-scoped record must carry an account identity before remote synchronization. No authentication or ownership enforcement is implemented here.

## Revision, tombstones, and synchronization state

`SyncMetadata` defines a contract version, ownership, optional account ID, non-negative revision pair, synchronization state, tombstone state, schema version, migration state, and update timestamp. A stale update is one whose last-known revision does not match the accepted record revision; detection and server enforcement are deferred. Deletions must eventually remain representable as tombstones until all relevant devices can observe them; current local deletion behavior is unchanged and compaction is deferred.

The states distinguish local-only, pending, syncing, synchronized, failed, and conflict conditions. They are descriptive contracts only; no queue or transport exists.

## Migration and schema

Migration states are `NOT_STARTED`, `PENDING`, `IN_PROGRESS`, `COMPLETED`, `FAILED`, and `REQUIRES_REVIEW`. Schema version is explicit and starts at `1` for this contract. Migration execution, merge decisions, export/import, and account switching belong to later milestones.

## Relationships and ordering

Business is the parent of inventory, customers, sales, and business expenses. Sales reference inventory and optionally customers; sale line items remain part of the sale aggregate. Categories are scoped to business or personal data and are referenced by budgets and finance records. Accounts, personal income, personal expenses, and budgets are personal finance records. Future synchronization should establish parents and referenced categories before dependent records, while preserving existing service-level stock and money rules.

## Repository implications

The existing UI → hooks → services → repository interfaces → Dexie repositories flow remains unchanged. P4.1 adds type-level contracts only and introduces no remote repository, network call, database migration, or UI behavior. Integer minor-unit money and currency separation remain untouched.

## Deferred work and risks

Authentication, provider selection, account lifecycle, device identity, encryption, durable sync queues, retries, remote authorization, migration execution, conflict resolution UI, tombstone compaction, and multi-device rollout remain deferred. The primary risks are accidental account attachment, financial conflict loss, relationship ordering errors, and local data loss; later milestones must address them with explicit review and recovery paths.

## Next authorization

P4.2 and later work are not started or authorized by completing P4.1. The project returns to `PAUSED_AWAITING_INSTRUCTIONS` after verification.
